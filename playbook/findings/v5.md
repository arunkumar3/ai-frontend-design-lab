# v5 — community design skills

Route `/v5`. Started as a copy of `/v4`. Lever: three installed community skill packs —
Emil Kowalski's animation skills, Impeccable, and the Taste anti-slop pack.
Commit `d1989e5`.

This drill exists to test one specific claim, from the post that prompted this project:

> Install all three first. Then just describe the website you want. **The skills kick in
> automatically as Claude builds.**

## That claim is false as written

**The Skill tool returned `Unknown skill` for all seven packs checked by name.** The
implementer reported it; I verified it independently from the main session:

```
Skill(impeccable) → Unknown skill: impeccable
```

The packs were installed correctly — 24 skill directories sit in `.claude/skills/` and
`.agents/skills/` (seven were individually invoked and confirmed `Unknown skill`; the rest
share the same locations and were not tested one by one). They were simply not
*discoverable* to the running session.

**An observation, not a confirmed mechanism.** One global `~/.claude/skills/` clone (`git
clone`, the `taste` DNA extractor) worked immediately; two project-local installs (`npx
skills add`, `impeccable skills install`, landing in `.claude/skills/` and
`.agents/skills/`) did not register at all. Both installs happened in the same session,
minutes apart. But install method and install location were never varied independently, so
this does not isolate a cause. Untested alternative explanations: the install method itself
(`git clone` vs. a package-manager install), the fact that **23 of the 24 entries in
`.claude/skills/` are symlinks into `../../.agents/skills/`** — only `impeccable` is a real
directory — and the possibility that project-local skill discovery is simply unsupported in
this session's Claude Code, independent of both.

**What is confirmed, and it is enough to act on: installation does not imply availability,
and nothing warns you.** "Install, then restart Claude Code" was proposed here as the fix
but was never tested — and it appears to be false. A direct check in a brand-new session
(`Skill(impeccable)`, a real directory, not even a symlink) still returns `Unknown skill`.
Do not repeat the restart advice; treat the cause as unconfirmed and **test with a direct
invocation before relying on a pack** — the same class of failure as `v1`'s inert `@theme`
block: a silent no-op that looks exactly like success.

## What v5 therefore actually measures

Not "skills kicking in." The implementer fell back to **reading each pack's `SKILL.md` and
applying its rules by hand**, plus running Impeccable's CLI, which works fine outside the
skill system (`npx impeccable detect`).

That is still a fair test of the *content* of the packs. It is not a test of the workflow
the post describes.

## Result: near-zero delta over v4

`/v4` and `/v5` are **layout-identical.** The only deltas are a 300ms Motion mount-time
stagger and a darkened light-mode accent for contrast (see below) — if you're comparing the
two screenshots and expecting a visual difference beyond that, there isn't one; this is not
a capture error.

| | v4 | v5 |
|---|---|---|
| Page height (1440 light) | 3742px | 3742px |
| `impeccable detect` findings (**live-browser scan**) | 3 | 3 |

These are live-browser numbers, not source-scan numbers — the source scan is the metric
`findings/RANKING.md` calls "worthless here and actively misleading," so it is not used for
this comparison. Identical height, identical live audit score. `v4` had already reached 15
of 17 tells with no regressions; there was little headroom, and the packs did not find it.

`v5` was not separately scored against the 17-item tell list: its layout is unchanged from
`v4`, so there is nothing new to score row-by-row, and doing so would just restate `v4`'s
15/17.

The three remaining live-audit findings are the same set in both: *hero eyebrow / pill
chip*, *line length too long*, and **"overused font: Instrument Serif."** The implementer
kept the typeface deliberately rather than rotating to the next fashionable face, and logged
the reasoning as a conflict. Given `v2` independently chose Fraunces and `v3` chose
Instrument Serif — both flagged — rotating again would have been theatre.

## The one thing the packs genuinely earned

**A real WCAG contrast failure, present since `v3`, that the automated detector missed.**

The region toggle's active pill rendered `#F5FFFE` on `#0E8C86` — **4.03:1**, below the
4.5:1 floor for body text at 14px/600. `impeccable detect` reported **zero** contrast
findings, in both file-scan and live-browser modes, on `/v4` and pre-fix `/v5`.

What caught it was the pack's own `craft-floor.md` instructing the reader to *compute the
values*. Fixed in `v5` by darkening the light-mode accent to `#0A6E69` (5.98:1).

In the implementer's words:

> a clean `impeccable detect` run is not proof of `craft-floor` compliance

**That is the finding: the checklist beat the scanner, in the same product.** The automated
tool gave a clean bill of health on a standard its own documentation defines. If you install
Impeccable and only ever run `detect`, you get the weaker half of it.

## Conflicts logged

Three substantive disagreements, in `playbook/findings/v5-conflicts.md`:

1. **Typeface** — three separate signals said change it; kept Instrument Serif + Inter.
2. **The eyebrow label** — a three-way split between packs; kept as-is.
3. **Entrance motion** — the animation pack wanted cinematic scroll choreography; shipped a
   300ms mount-time stagger instead, partly because scroll-triggered motion does not survive
   a full-page screenshot.

Notable: **all three of the packs' strongest opinions were overridden.** Not because the
packs are wrong in general, but because each opinion was formed without knowledge of this
product's constraints — a capture harness, a frozen comparison set, a deliberate prior
decision about typography.

## Verdict on the post's claim

The post says the skills "get you 90% there." On this evidence, applied to a page that had
already been through a constitution, a token system, references, and a screenshot loop:

- **The workflow it describes does not work as written** (project-local packs were not
  discoverable; a restart did not fix it either).
- **The packs' content contributed one real fix** — a genuine accessibility bug — and a set
  of opinions that were correctly overridden.
- **The screenshot loop (`v4`) contributed far more**, and cost nothing to install.

Installed taste is worth having. It is not a substitute for looking at your own output, and
it is nowhere near 90% of the distance.
