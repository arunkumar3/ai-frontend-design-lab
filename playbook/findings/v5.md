# v5 — community design skills

Route `/v5`. Started as a copy of `/v4`. Lever: three installed community skill packs —
Emil Kowalski's animation skills, Impeccable, and the Taste anti-slop pack.
Commit `d1989e5`.

This drill exists to test one specific claim, from the post that prompted this project:

> Install all three first. Then just describe the website you want. **The skills kick in
> automatically as Claude builds.**

## That claim is false as written

**The Skill tool returned `Unknown skill` for all seven packs.** The implementer reported
it; I verified it independently from the main session:

```
Skill(impeccable) → Unknown skill: impeccable
```

The packs were installed correctly — 23 skill directories sit in `.claude/skills/` and
`.agents/skills/`. They were simply not *discoverable* to the running session.

**The mechanism, and it is a clean asymmetry:**

| Location | Installed by | Hot-reloads mid-session? |
|---|---|---|
| `~/.claude/skills/` | `git clone` (the `taste` DNA extractor) | **yes** — announced and usable immediately |
| `.claude/skills/`, `.agents/skills/` | `npx skills add`, `impeccable skills install` | **no** |

Both installs happened in the same session, minutes apart. The global one became available
at once. The project-local ones did not register at all.

**So the honest instruction is: install the packs, then restart Claude Code.** "Install in
seconds" is true. "They kick in automatically" is not, unless you restart — and nothing
warns you. You get a silent no-op that looks exactly like success, which is the same class
of failure as `v1`'s inert `@theme` block.

## What v5 therefore actually measures

Not "skills kicking in." The implementer fell back to **reading each pack's `SKILL.md` and
applying its rules by hand**, plus running Impeccable's CLI, which works fine outside the
skill system (`npx impeccable detect`).

That is still a fair test of the *content* of the packs. It is not a test of the workflow
the post describes.

## Result: near-zero delta over v4

| | v4 | v5 |
|---|---|---|
| Page height (1440 light) | 3742px | 3742px |
| `impeccable detect` findings | 1 | 1 |

Identical height, identical audit score. `v4` had already reached 15 of 17 tells with no
regressions; there was little headroom, and the packs did not find it.

The one remaining audit finding is the same in both: **"overused font: Instrument Serif."**
The implementer kept it deliberately rather than rotating to the next fashionable face,
and logged the reasoning as a conflict. Given `v2` independently chose Fraunces and `v3`
chose Instrument Serif — both flagged — rotating again would have been theatre.

## The one thing the packs genuinely earned

**A real WCAG contrast failure, present since `v3`, that the automated detector missed.**

The region toggle's active pill rendered `#F5FFFE` on `#0E8C86` — **4.03:1**, below the
4.5:1 floor for body text at 14px/600. `impeccable detect` reported **zero** contrast
findings, in both file-scan and live-browser modes, on `/v4` and pre-fix `/v5`.

What caught it was the pack's own `craft-floor.md` instructing the reader to *compute the
values*. Fixed in `v5` by darkening the light-mode accent to `#0A6E69` (5.98:1).

In the implementer's words:

> a clean `impeccable detect` run is not proof of `craft-floor` compliance

**That is the finding: the checklist beat the scanner, in the same product.** The automated
tool gave a clean bill of health on a standard its own documentation defines. If you install
Impeccable and only ever run `detect`, you get the weaker half of it.

## Conflicts logged

Three substantive disagreements, in `playbook/findings/v5-conflicts.md`:

1. **Typeface** — three separate signals said change it; kept Instrument Serif + Inter.
2. **The eyebrow label** — a three-way split between packs; kept as-is.
3. **Entrance motion** — the animation pack wanted cinematic scroll choreography; shipped a
   300ms mount-time stagger instead, partly because scroll-triggered motion does not survive
   a full-page screenshot.

Notable: **all three of the packs' strongest opinions were overridden.** Not because the
packs are wrong in general, but because each opinion was formed without knowledge of this
product's constraints — a capture harness, a frozen comparison set, a deliberate prior
decision about typography.

## Verdict on the post's claim

The post says the skills "get you 90% there." On this evidence, applied to a page that had
already been through a constitution, a token system, references, and a screenshot loop:

- **The workflow it describes does not work as written** (no discoverability without restart).
- **The packs' content contributed one real fix** — a genuine accessibility bug — and a set
  of opinions that were correctly overridden.
- **The screenshot loop (`v4`) contributed far more**, and cost nothing to install.

Installed taste is worth having. It is not a substitute for looking at your own output, and
it is nowhere near 90% of the distance.
