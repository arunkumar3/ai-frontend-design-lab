# v1 — the constitution

Route `/v1`. Lever added: a repo-root `CLAUDE.md` design constitution. Nothing else —
same naive prompt, no references, no screenshot iteration, no design skills.
Commit `a15f9eb`.

## Did the mechanism even work?

Yes, and this was worth testing separately. **`CLAUDE.md` was never mentioned in the
dispatch prompt.** The implementer was asked afterwards whether it had received any
repository-level instructions; it reported that the Design Constitution was supplied
automatically and named the specific decisions it drove (single accent, four-size type
scale, asymmetric non-`mx-auto` layout, explicit light/dark tokens).

**A standing `CLAUDE.md` does reach delegated subagents and does change their output
without being restated.** That is the load-bearing claim behind the whole technique, and
it holds.

## The finding that matters

Only **three** of the nine fixes correspond to a rule the constitution actually states:

| Fixed tell | Constitution rule that caused it |
|---|---|
| T9 colour identity | "Exactly one accent color across the page" |
| T10 type scale | "No more than four sizes on one screen" |
| T2 left-hugging | "Asymmetry somewhere" + `max-w-7xl mx-auto` banned |
| T14 elevation | `shadow-lg` banned; "elevation must be earned" |

The other five — T4 ragged heights, T5 fallback state, T8 fallback dominance, T11 flat
metadata, T12 duplicated date — are **nowhere in the constitution**. Nothing instructed
the model to fix them. They improved anyway.

The plausible mechanism: a document declaring that design is being taken seriously raises
the general standard, not only the enumerated items. The ban list is the visible part;
the invisible part is the signal that someone is watching.

This reframes what a `CLAUDE.md` is for. It is not primarily a filter that catches listed
mistakes — it is a stance that changes the level of care. Which also means **you cannot
predict its effect from its contents**, and the only way to know what it bought is to
compare captures.

## Where the constitution was blind

**T16 was fixed by accident, and v0 was factually wrong.** Today is 2026-08-15. `v0`
put a "New today" badge on the Aug 16 group — simply incorrect. `v1` puts "TODAY" on the
Aug 15 group, which is right. No constitution rule covers date correctness; `v1` just
reasoned better.

**T1, T3, T6, T13, T17 are untouched** because the constitution says nothing about grid
behaviour with variable-length groups, content-type differentiation, fallback legibility,
decorative affordances, or contrast minimums. A ban list only bans what its author already
thought of — which is exactly the ceiling this drill exists to measure.

## The regression

**T7 got worse.** `v0`'s fallback used two-letter initials: `BB`, `BB`, `IT`, `ID`.
`v1` reduced them to one letter, so the Aug 15 row now shows **`I` and `I` adjacent**
(*India Tour of Sri Lanka*, *IndianOil Durand Cup 2026*) and **`B` and `B`**
(*Bharat Bhagya Vidhaata*, *Bigg Boss Agnipariksha*). Fewer characters, more collisions.

A refinement that improves the visual and degrades the information. Nothing in the
constitution guards against that, because the constitution is written in the language of
appearance, not of meaning.

**And the accent rule is only half-honoured.** The hatched no-artwork panels are tinted
by *platform brand colour* — pink for SonyLIV, blue for JioHotstar, purple for ZEE5. So
"exactly one accent colour" is satisfied for the page chrome while eleven borrowed brand
colours still leak through the content. T9 is partial, not fixed.

## Amendment — a Tailwind v4 trap that nearly became a confound

The first `v1` captures were taken with its display font silently not applying.

`v1.css` declared `@theme { --font-display: Georgia, ... }` and was imported from
`V1.jsx` with a JS `import './v1.css'`. **`@tailwindcss/vite` only processes `@theme`
inside the CSS module graph rooted at the file containing `@import "tailwindcss"`** — here,
`lab/src/index.css`. A route-local CSS file imported from a component is outside that
graph, so the `@theme` block shipped to the browser verbatim, the browser ignored it, and
`--font-display` resolved to `""`.

There is **no dev-time error**. `vite build` emits `Unknown at rule: @theme` and keeps
going. The only reliable detection is checking computed style in a real browser:

```js
getComputedStyle(document.documentElement).getPropertyValue('--font-display')  // ""
```

The implementer's own report claimed a "serif display face" that was never in the pixels.
It believed its own intent rather than checking the output — the exact failure the `v4`
screenshot-loop drill exists to address, showing up two drills early and by accident.

Fixed at `c48e4fd` by moving the token out of the inert `@theme` block. Re-captured.
Verified: `<h1>` computed `font-family` now resolves to the serif stack, `vite build` is
warning-free, no `@theme` survives in the built CSS, and `/v0` renders unchanged.

**Scoring impact: none.** The change is confined to the headline and the fallback monogram
letters; layout, colour, and structure are pixel-identical. T10 was scored on size
hierarchy, not typeface, so all 17 verdicts stand as recorded.

**This invalidated Task 6 as originally written**, which specified `@theme` in
`lab/src/routes/v2/theme.css` — precisely the dead path. Drills `v2`–`v5` use the
mechanism proven here instead.
